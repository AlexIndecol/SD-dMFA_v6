# Variables and Parameters Taxonomy

This document is the canonical reference for the difference between:

1. exogenous variables,
2. endogenous variables,
3. parameters.

It is runtime-facing and operational. It is meant for scenario authors, model maintainers, and reviewers.

## Document position

- You are here: Tier 2 canonical model taxonomy reference.
- Canonical scope: definitions and exhaustive lists for exogenous variables, endogenous variables, and parameters.
- Out of scope: full formula derivations and scenario narrative design.
- Related docs: [INDICATORS.md](./INDICATORS.md), [CONFIGS.md](../workflows/CONFIGS.md), [SCENARIOS.md](../workflows/SCENARIOS.md), [ARCHITECTURE.md](./ARCHITECTURE.md), [MODEL_GOVERNANCE.md](../governance/MODEL_GOVERNANCE.md)

## 1) Purpose and scope

Use this page to answer three practical questions quickly:

1. Is this quantity read from data (`exogenous`) or produced by the model (`endogenous`)?
2. Is this quantity a control input (`parameter`) rather than a data series or model result?
3. Where is this quantity defined, applied, and checked?

Primary source-of-truth files for this page:

- `registry/variable_registry.yml` (exogenous variables)
- `configs/indicators.yml` (endogenous indicator names)
- `configs/runs/_core.yml` (parameter groups and baseline keys)
- `src/crm_model/config/models.py` (accepted config surfaces)
- `src/crm_model/cli.py` and `src/crm_model/coupling/runner.py` (runtime export and diagnostics fields)

## 2) Three-group definition map

## 2.1 Exogenous variables

What this is:
- Data read from external files before or during run setup.
- Declared in the variable registry and validated before runs.

What this is not:
- Not produced by SD/MFA/OD runtime dynamics.
- Not a behavior control surface by itself.

Operational test:
- If it comes from `data/exogenous/...` and is listed in `registry/variable_registry.yml`, it is exogenous.

## 2.2 Endogenous variables

What this is:
- Quantities generated by model dynamics during execution.
- Exported to run outputs (`timeseries.csv`, `scalar_metrics.csv`, coupling diagnostics, OD diagnostics).

What this is not:
- Not directly loaded from exogenous CSV files.
- Not config knobs.

Operational test:
- If it appears as runtime output in `outputs/runs/...` and is computed from SD/MFA/OD state updates, it is endogenous.

## 2.3 Parameters

What this is:
- Config-controlled values that shape behavior, policy logic, routing, and scenario stress setup.
- Defined in run/scenario config blocks such as `sd_parameters`, `strategy`, `shocks`.

What this is not:
- Not observational data series from external sources.
- Not post-simulation diagnostics.

Operational test:
- If you edit it in `configs/runs/*.yml` or `configs/scenarios/*.yml` to change model behavior, it is a parameter.

## 3) How to classify a quantity (decision rules)

Use this sequence:

1. Is it loaded from a file declared in `registry/variable_registry.yml`?
- Yes -> `exogenous variable`.
- No -> go to step 2.

2. Is it a configurable control in run/scenario YAML (`sd_parameters`, `mfa_parameters`, `strategy`, `transition_policy`, `demand_transformation`, `shocks`, `sd_heterogeneity`, `scenario_profiles`)?
- Yes -> `parameter`.
- No -> go to step 3.

3. Is it computed during runtime and exported as indicator/diagnostic output?
- Yes -> `endogenous variable`.
- No -> treat as internal implementation detail until explicitly surfaced.

## 6) Parameters list (canonical control surfaces)

Parameter groups below are runtime-accepted surfaces in run and scenario configs.

What it controls:
- SD dynamics and coupling sensitivity (price response, bottlenecks, collection controls, capacity envelope, coupling gains).

Where applied:
- SD solver and coupling loop setup before each coupled iteration.

Current baseline keys in `_core.yml`:
- `price_base`
- `price_scarcity_sensitivity`
- `demand_price_elasticity`
- `coupling_service_stress_gain`
- `coupling_circular_supply_stress_gain`
- `coupling_signal_smoothing`

- `capacity_envelope_initial`

## 6.2 `mfa_parameters`

What it controls:
- Core MFA physical parameters (yields, collection base, mass-balance tolerance).

Where applied:
- MFA run setup and per-year flow resolution.

Current baseline keys in `_core.yml`:
- `fabrication_yield`
- `collection_rate`
- `recycling_yield`
- `reman_yield`
- `mass_balance_tolerance`

Common mistakes:
- Duplicating overlapping keys in `strategy` without clear override intent.

Interaction notes:
- Scenario overrides can be gated/ramped and are merged before runtime execution.

## 6.3 `strategy`

What it controls:
- Behavioral/policy routing and inventory controls close to MFA operation.

Where applied:
- MFA routing, stock release, and strategic reserve behavior during coupled execution.

Current baseline keys in `_core.yml`:
- `reman_yield`
- `lifetime_multiplier`
- `refinery_stockpile_release_rate`
- `new_scrap_to_secondary_share`
- `strategic_reserve_enabled`
- `strategic_reserve_target_coverage_years`
- `strategic_reserve_fill_gain`
- `strategic_reserve_release_gain`
- `strategic_reserve_max_fill_rate`
- `strategic_reserve_max_release_rate`
- `strategic_reserve_fill_price_threshold`
- `strategic_reserve_release_price_threshold`
- `strategic_reserve_fill_service_threshold`
- `strategic_reserve_release_service_threshold`

Common mistakes:
- Treating `strategy` as a generic catch-all instead of targeted routing/policy controls.
- Keeping old collection multiplier keys under `strategy` (no longer supported).

Interaction notes:
- For some overlapping yield/routing paths, strategy values act as intended runtime override surfaces above base MFA params.

## 6.4 `transition_policy`

- Adoption/compliance dynamics and policy-derived uplifts/relief.

Where applied:
- Transition adoption is built per year and can adjust SD/MFA/strategy channels during runtime.

Current baseline keys in `_core.yml`:
- `enabled`
- `start_year`
- `adoption_target`
- `adoption_lag_years`

## 6.6 `shocks`

What it controls:
- Discrete stress events with `start_year`, `duration_years`, `multiplier` structure.

Where applied:
- SD and MFA channels depending on shock type.

Current baseline shock channels in `_core.yml`:
- `demand_surge`
- `recycling_disruption`
- `primary_refined_output`
- `trade_refined_import_need_multiplier`
- `trade_concentrate_import_need_multiplier`
- `trade_scrap_import_need_multiplier`
- `trade_export_capacity_multiplier`
- `extraction_yield`
- `beneficiation_yield`
- `refining_yield`
- `sorting_yield`
- `collection_rate`
- `recycling_rate`
- `remanufacturing_rate`
- `disposal_rate`
- `strategic_fill_intent`
- `strategic_release_intent`

Common mistakes:
- Using shocks for structural transitions that should be ramps.

Interaction notes:
- Reporting phase applies gating/clamping behavior for temporal enforcement.

## 6.7 `sd_heterogeneity`

What it controls:
- Ordered rule-based SD parameter differences by material and/or region.

Where applied:
- Applied before variant-level SD overrides for each slice.

Current structure:
- each rule: `name`, optional `materials`, optional `regions`, `sd_parameters`.

Common mistakes:
- Adding broad overlapping rules without intentional order.

Interaction notes:
- Later matching rules override earlier matching rules.

## 6.8 `scenario_profiles` and phase context

What it controls:
- Profile CSV ingestion and precedence behavior for reporting runs.

Where applied:
- Profile payload is overlaid on variant payload in reporting phase.

Current keys in `_core.yml`:
- `enabled`
- `csv_globs`
- `interpolation`
- `apply_precedence`
- `emit_resolved_payload`

Common mistakes:
- Enabling profiles without matching CSV files/rows for the active variant.

Interaction notes:
- In reporting phase, profile payload can supersede variant values on overlapping paths.

## 7) Comparison of scenario control blocks

This section compares the most commonly confused control blocks.

| Block | Primary intent | Typical temporal pattern | Runtime application stage | Typical use | Precedence notes |
|---|---|---|---|---|---|
| `mfa_parameters` | Base physical MFA controls | Scalar, year-gated, full timeseries, ramp reference | MFA setup and per-year flow accounting | Change collection/yield/loss baseline behavior | Overridden by scenario/global and dimension overrides; some overlapping runtime strategy controls intentionally supersede base values |
| `strategy` | Routing and operational policy controls near MFA execution | Scalar, year-gated, ramp reference | Routing resolution, stock release, strategic reserve controls | Circular routing strategy, stock release policy, reserve behavior | Applied after merge layering; meant for intentional runtime control surfaces |
| `transition_policy` | Policy adoption and compliance dynamics | Usually enabled gate + year-gated policy trajectory | Transition adoption build and policy uplift application | Policy acceleration and delayed adoption scenarios | Merged like other blocks; often interacts with demand transformation and SD/MFA parameter adjustments |
| `demand_transformation` | Demand-side decomposition and efficiency/rebound control | Enabled gate + year-gated or ramp multipliers | Demand transformation function before coupled demand handoff | Demand structure scenarios (activity/intensity/efficiency) | Reporting-phase enforcement and profile overlays apply where configured |
| `shocks` | Acute event stress channels | Event form (`start_year`, `duration_years`, `multiplier`) | Channel-specific shock application in SD/MFA/trade paths | Crisis windows, disruptions, temporary stress tests | Global + dimension overrides; reporting-phase clamp/enforcement applies in reporting runs |

## 8) Maintenance workflow (manual + checklist)

Use this workflow every time model interfaces change.

## 8.1 Update triggers

Update this document when any of these happen:

1. A registry entry is added, removed, renamed, or reclassified required/optional.
2. Indicator names or logical subsets change in `configs/indicators.yml`.
3. Parameter surfaces or baseline keys change in `_core.yml` or config models.
4. Runtime merge/precedence behavior changes in scenario/coupling/CLI code.

## 8.2 Update steps

1. Refresh exogenous list from `registry/variable_registry.yml`.
2. Refresh endogenous list from `configs/indicators.yml` and runtime diagnostics exports.
3. Refresh parameter-group lists from `configs/runs/_core.yml` and accepted surfaces in `src/crm_model/config/models.py`.
4. Run the validation checklist below.
5. Update cross-links in `docs/README.md` and `README.md` only if section names/paths changed.
